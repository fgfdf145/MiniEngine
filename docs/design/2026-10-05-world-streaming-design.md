# 大地图流式加载设计（2026-10-05）

## 背景

GTA SA 全图（5 个区域）一次性载入：31k submesh、19k 贴图、820 万三角形，启动要 45 s，显存 3.6 GB。地图只会越来越大，所以要改成按相机/车辆位置流式加载。

## 目标

- 只把焦点（Play 时是车，否则是相机）附近的格子以高模（HD）载入，其余格子显示游戏自带的 LOD 模型，整张地图始终可见。
- 进出格子不卡帧：模型在后台线程解析，贴图走现有的异步准备队列，GPU 上传只处理增量。
- 开车不依赖流式状态：碰撞和水面始终全图载入（数据量小，Play 启动时构建约 1.3 s）。
- 流式产生的实体只在运行时存在：不存进场景文件、不出现在场景面板、不抢选择。

## 数据（GTASA MAP/tools/engine_bundle.py --stream）

`out/engine/gtasa_stream/`，安装到 `assets/models/gtasa_stream/`：

| 路径 | 内容 |
|---|---|
| `hd/<区域>_<cx>_<cy>.gltf/.bin` | 每 500 m 格子的高模（已按材质合批，同现在的区域模型） |
| `lod/<区域>_<cx>_<cy>.gltf/.bin` | 同一格子的 LOD 模型（游戏 `*_lod` 物体）；每个 LOD 物体归入引用它的高模物体所在的格子，保证同一格子 HD/LOD 互斥时没有缝或重叠 |
| `textures/<txd>/<纹理>.png` | 所有格子共用的贴图（硬链接） |
| `gtasa.stream.yaml` | 清单：每个格子的 hd/lod 路径与世界空间包围盒 |

只有 LOD、没有 HD 的格子在近处也一直显示 LOD。格子可以标 `far_only: true`（2026-10-06）：只在半径以外显示 LOD，半径以内什么都不显示。用于 GTA3 的整岛 LOD（IslandLOD*）：包围盒就是整座岛，只要岛上任何一个格子是高模，整岛 LOD 就不显示，不会盖在街道上。

碰撞另出 `gtasa_collision_<区域>`（只有 `MINIENGINE_collision` 节点、不绘制），作为普通实体放进场景。

## 引擎

### 场景

场景 YAML 增加可选的顶层 `streaming`：

```yaml
streaming:
  - manifest: assets/models/gtasa_stream/gtasa.stream.yaml
    load_radius: 700     # 焦点到格子包围盒的水平距离小于它时载入高模
    unload_radius: 900   # 大于它时退回 LOD（滞回，防止边界来回切换）
    high_detail_only: true  # 可选（2026-10-07）：不论远近所有格子都用高模，从不载入 LOD；
                            # 只有 LOD 的格子（含 far_only）不显示，半径不再起作用
```

### WorldStreamingService（engine/editor/services）

每帧：

1. 焦点 = 正在驾驶的车，否则相机。
2. 每个格子按距离决定想要 HD 还是 LOD（带滞回）。
3. 需要但不在模型缓存里的模型交给后台加载线程（一次一个，按距离由近到远；模型加载器不能并发读同一文件）。
4. 模型已在缓存中的格子在主线程换实体：先建新实体（HD 或 LOD），同一帧删掉旧的。CPU renderable 按实体增量更新；渲染端等这次变更的贴图全部准备好后才一次性提交，所以不会看到白模或空洞。
5. 流式实体带 `StreamedComponent`：存档、场景面板、选择都跳过它们；模型缓存按引用自动淘汰不再使用的格子。

`--wait-for-scene` 把"焦点附近的格子还没到位"也算作加载中，截图不会截到一半。

### 渲染端增量上传

`UploadSceneResources` 以前每次变更都重建全部 submesh 缓冲。现在 `RenderSubmesh::buffer` 是共享指针，按 CPU mesh 指针复用已在 GPU 上的缓冲；贴图本来就按 key 复用。描述符集、逐绘制数据和光追场景后来也改成了增量的，见文末"实现补充"。

## 验收

- 启动时间、显存、三角形数与全图载入对比。
- 相机以固定速度穿越地图（`--camera-velocity`）录像：格子切换没有空洞，记录切换帧的最长帧时间。
- 在流式场景里试驾（`--drive`），车在所有格子上都有碰撞，开进海里照样下沉。

## 实现补充：切换不卡顿（2026-10-05）

格子切换时的卡顿来自"每次内容变化都按全部已载入内容重做"。现在一次变化只处理增减的部分：

- **渲染子网格**：每个 CPU 子网格有一个修订号（`CpuRenderSubmesh::revision`），GPU 端的 `RenderSubmesh` 按修订号缓存、共享；变化时只为新的子网格建对象。
- **绘制槽位**：每个子网格占一个固定的绘制槽位（`drawSlot`，即 firstInstance），材质、贴图变换、上一帧模型矩阵和光追材质都按槽位存放；只写新槽位，释放的槽位回收；缓冲容量不够时才按 1.5 倍扩容。
- **贴图与材质描述符集**：贴图放在按键值的常驻表里并计数引用（`m_textureStore`），材质描述符集按 32 个绑定缓存并计数（`VulkanMaterialSetCache`）；子网格进来时加引用，离开时减引用，归零的在提交时释放。描述符集从按集计数的池列表分配（`VulkanDescriptorPoolList`），不再挨个试已满的池。
- **光追场景**：光追材质按槽位存放，只对新槽位做平均；网格层级的 GPU 缓冲和全量顶层结构都在后台线程建好，安装时只交换句柄；旧的构建结果在后台任务里释放。
- **诊断**：帧计时日志里有 CPU 各阶段和最慢一帧；超过 33 ms 的帧会打印各阶段耗时（"Slow frame"）。

实测（GTA SA，相机 130 km/h 移动 1 分钟）：载入完成后 43 秒、约 60 次格子切换里只有 3 帧在 35–45 ms，其余都在正常帧时间内；静止时一次提交从 60–110 ms 降到 5–10 ms。

## 实现补充：硬件光追之后的切换卡顿（2026-10-07）

加入硬件光追（BLAS/TLAS）和三张地图合一之后，开车进入新区域又明显卡顿：每次格子变化（全图约每秒一次）渲染线程都有一帧 45–60 ms，内容接连变化时还有 200–450 ms 的帧。分段计时找到四处：

- **顶层加速结构按内容精确定大小**：每次安装都按新的实例数销毁、重建每个帧槽位的 TLAS（存储、scratch、实例缓冲）和顶层节点/实例缓冲，而流式内容的实例数每次都差一点，一次约 40 ms 的分配。现在容量留出 1/4 的增长空间，只有超出或降到一半以下（换成小场景）才重建（`InstanceCapacity`，`ray_scene.cpp`）。
- **释放上一份网格层级缓冲**：软件光追的节点/三角形缓冲在全图上约 500 MB（硬件光追的命中着色也读三角形），每次安装后在后台任务里 `vkFreeMemory`，约 36 ms，期间驱动锁让渲染线程的 Vulkan 调用同样等 30 ms。现在这些大缓冲（≥ 4 MB）放回备用池，下一次构建直接复用（`AcquireBuffer` / `RecycleBuffer`），常驻多占一份系统内存（约 500 MB 映射内存）。
- **被取代的构建照样建缓冲**：内容接连变化时几次构建同时在跑，每次都分配、填满自己的几百 MB 缓冲再整个扔掉。现在构建一旦被新内容取代（`m_pendingSuperseded`），只把层级和 BLAS 留给后面的构建，不再建缓冲和顶层。
- **贴图暂存等整个队列空闲**：每帧暂存新贴图的批次 `Flush` 用 `vkQueueWaitIdle`，连同在途的帧一起等，约 10 ms。现在批次提交后不等（`VulkanUploadBatch::SubmitWithoutWait`：结尾一个全局屏障保证之后的提交看得到拷贝和布局转换，栅栏到了才释放暂存内存）。试过按约 2 ms 的时间预算少暂存几张，结果提交（要等这次变化的贴图全部就绪）一直等不到，待处理的子网格越积越多，RequestUpload 每帧 50 ms 以上，所以仍是每帧最多 64 张。

实测（Release，RTX 4070 笔记本，隐藏窗口 1080p，GTA 全图，相机 0.4 m/帧向西飞 3000 帧，`--wait-for-scene`）：

- 每次安装 RayInstall 45–55 ms → 3–4 ms，不再有释放带来的驱动等待。
- 整次运行（载入、移动，以及都碰上的显存预算收缩）超过 33 ms 的渲染帧：修改前 170 帧，最长 458 ms（RayInstall 37、StageTextures 36、CommitContent 87）；修改后 46–52 帧，最长 117–148 ms，几乎都是提交本身（CommitContent）。没有预算收缩的一次修改前运行里，移动阶段 71 次内容变化有 78 个慢帧（66 个 RayInstall），修改后约 0.5 个慢帧一次变化。
- Debug 加验证层跑约 260 次格子变化，没有验证错误。

隐藏窗口在 4K 屏上会预留 3.2 GB 的全屏余量，Windows 下调预算时常常整片卸载，所以全图的帧数统计每次差别很大；比较时按慢帧的主要阶段分类，或者用固定半径的场景。

仍未处理：提交本身（CommitContent 15–25 ms：等在途帧的 `WaitForAllFrames`、有新缓冲时上传批次的等待约 6 ms、按全部子网格做的准备约 5 ms）；RequestUpload 每次都遍历所有未提交的子网格；Windows 显存预算下调时预算半径大幅收缩、整片卸载再载入。

## 实现补充：提交本身的卡顿（2026-10-07）

上一节之后，每次格子变化剩下的主要是提交（CommitContent，全图 15–25 ms）和贴图暂存。分段计时（全图约 2.2 万个子网格）：上传里等 GPU 排空和为每个新网格建缓冲、按全部子网格重建的 mesh→缓冲表（固定 2.5 ms）、kept/dropped 的哈希集合、光追输入、`SetContent` 复制子网格列表、扫描全部 1.4 万张贴图找没人引用的；另外光追安装和删除实体时各有一次 `WaitForAllFrames`，`Motion` 在内容变化的帧重建两个节点式哈希表（3 ms），新格子的几百个 BLAS 在同一帧压缩（40 ms）。

改法：

- **退役队列**（`VulkanRetireQueue`）：在途帧可能还在用的东西（旧贴图、被丢掉的子网格及其缓冲、材质描述符集、光追材质槽的集合、绘制槽位、上一份光追内容和 BLAS）不再先等 GPU 排空再销毁，而是记下当时的提交序号，等下一帧的围栏也到了再释放（`VulkanCommandContext::LastSubmit/CompletedSubmits`；多等一帧是因为本帧里先提交的上传批次只有后面帧的围栏能覆盖）。绘制槽位退役后才能再分配，所以往空槽写新绘制不用等。
- **不等 GPU 的提交**：提交里的上传批次也 `SubmitWithoutWait`；光追的贴图表加 `VK_DESCRIPTOR_BINDING_UPDATE_UNUSED_WHILE_PENDING_BIT`（设备支持时），只写新放入的槽位，释放的槽位不动（之后没有实例指向它，表是 partially bound）；只有每绘制缓冲扩容时才等。
- **不等 GPU 的光追安装**：每个帧槽位自己的描述符集在该槽位下一次 `UpdateInstances` 时才指向新内容，旧内容退役；只有实例容量变化（重建 TLAS 和槽位缓冲）时才等。
- **增量化**：mesh→缓冲表常驻（弱引用并核对 mesh 本身）；按实体连续计数子网格序号；kept 用提交序号标记；光追输入并行生成；`SetContent` 和安装共享同一份子网格列表（`shared_ptr`），逐网格的输入在 worker 上整理；不透明标志只更新换手的槽位；只检查引用归零的贴图。`MotionHistory` 换成开放寻址的扁平表。
- **分帧**：新网格的 GPU 缓冲在准备贴图的那几帧里先建好（每帧约 2 ms 或帧时间的 15%），贴图就绪后提交不再等它们，剩下的由提交自己建；暂存的贴图和缓冲用一个批次，每帧约 4 ms 或帧时间的 30%、至少 32 张贴图；积压超过 1024 张贴图或 2048 个网格时不限时间；提交不和暂存同一帧；上传批次的 32 MB 暂存块放进池里复用（`VulkanStagingChunkPool`，每批省约 1 ms）；BLAS 压缩每帧最多 64 个。

实测（Release，全图，隐藏窗口 1080p，相机 0.4 m/帧，两次交替运行，对比上一节之后的 main）：移动阶段约 60 次内容变化里，渲染线程超过 12 ms 的帧 74/66 → 15/18，超过 20 ms 的 26/22 → 3/4；每次提交的上传平均 5.5 → 1.3 ms（最长 28 → 9），应用 5.2 → 1.1 ms；换格子的帧大多在 14 ms 以内（平时 5–8 ms）。新格子从变化到提交的延迟 Release 不变（约 0.05 s）；Debug 帧长（约 90 ms），按帧时间比例的预算和贴图下限让它保持在 0.4 s（原来 0.3 s）。Debug 加验证层在硬件光线查询、`--software-rays`、`--no-ray-query` 三种模式下都没有验证错误；测试全部通过。

仍未处理：偶发的一帧 40–60 ms 停在并行循环（ShadowDrawItems/RecordShadows/DrawItems）上，修改前也有（后台构建占满 worker 时，帧的子任务被抢占）；Windows 显存预算下调时的整片卸载。

## 实现补充：启动阶段的卡顿（2026-10-08）

上面几节处理的是走动中换格子；地图第一次加载（几秒内到达约 3 万个子网格、1.8 万张贴图）仍然有一串 80–150 ms 的帧。复现：`MINIENGINE_STREAMING_BUDGET_RADIUS=10000`（新环境变量，固定流式预算半径，不随显存预算变化，结果可重复）+ 白天路径追踪场景 + `MINIENGINE_FRAME_TIMES`，Release，隐藏窗口，900 帧（移动）或 600 帧（静止）。修改前的大帧来自：一次提交 1.5 万个新子网格（CommitContent 111–125 ms），每绘制缓冲连续多次扩容（每次重写全部绘制、光追材质和贴图表），从 ReBAR 显存用 CPU 读回光追材质缓冲（13.5 ms），光追实例容量逐个小步增长（RayInstances 76–135 ms，连续 3 帧），内存池在块空了就 `vkFreeMemory`、马上又分配，以及后台 BVH 构建占满所有 worker 时帧自己的并行循环只能在渲染线程上跑（RecordScenePasses 49 ms）。

改法：

- **分帧提交**：一次提交里新子网格的制作时间（只计新建的，不计 kept 的遍历）超过 5 ms 且已做了至少 256 个，剩下的留给后面几帧的提交，`m_sceneUploadPending` 保持为真；还在等待时 `UploadSceneResourcesOrKeepPrevious` 直接返回，不释放已准备的缓冲和暂存贴图。
- **请求去重**：`m_requestedRevisions` 记下已请求过贴图和缓冲的新子网格，之后的变化只请求自己的（原来每来一个格子就把所有待提交子网格的贴图再遍历一遍，5–15 ms）；提交后剪掉已上 GPU 的。
- **一次扩到位**：分帧提交时 `m_drawSlotReserve` = 变化的总子网格数的 4 倍（上限 65536，至少 1.25 倍），每绘制缓冲直接扩到它；扩容至少翻倍。光追实例容量至少翻倍；贴图表至少 65536 槽；`VulkanUniformBuffer` 构造时不再预填全部槽位（绘制拿到槽位时才写）。
- **光追材质缓冲**：平均材质的输出缓冲从每槽位的描述符集移到一个共享的 set 1（每槽位只剩两个采样器），扩容时新建缓冲，在下一次 `Record` 里用 `vkCmdCopyBuffer` 在 GPU 上拷贝旧内容，旧缓冲退役。
- **内存池保留空块**：`VulkanMemoryPool::Free` 不再释放空块；渲染帧里 `ReleaseEmptyBlocks(device, 4, 1)` 每帧最多释放一个、保留 4 个空块；设备销毁前全部释放。
- **贴图暂存硬上限**：有积压时预算至少 10 ms，但无论积压多少，一帧暂存超过 15 ms 就停。
- **被替代的光追构建**：被新构建替代的构建不再继续建剩下的 BVH，建好的立刻放进缓存给替代它的构建用，不再拼接整张地图（几百 MB 拷贝）。BVH 构建的 `ParallelFor` 最多占四分之一的 worker：一个 worker 进了一个网格要一直建完（大网格几十毫秒），全占满时帧的并行循环只能在渲染线程上跑。

实测（Release，同一复现，修改前 → 修改后，每帧渲染线程 CPU 时间）：

| 运行 | >20 ms 帧数 | >33 ms 帧数 | 最长 |
|---|---|---|---|
| 移动（3 次） | 72–79 → 8 / 11 / 12 | 7 → 0 / 0 / 2 | 145–152 → 29 / 30 / 45 ms |
| 静止（2 次） | 78 → 13 / 12 | 7 → 0 / 1 | 153 → 29 / 39 ms |

全图约 17 次分帧提交，每次 8–13 ms 上传 + 3–5 ms 应用（第一次应用 17–19 ms，含光追场景首次安装）。验证层下整段启动没有验证错误；测试全部通过（123/123）。

仍未处理：剩下的 >20 ms 帧主要是分帧提交本身（3 万个子网格时每次提交仍有 O(n) 的遍历）和光追安装（10–20 ms）；同时有其他 GPU 程序运行时的帧间隔尖峰不在渲染线程里。
